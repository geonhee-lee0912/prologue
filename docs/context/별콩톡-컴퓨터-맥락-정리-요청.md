이 문서의 요청 A는 로컬 메모리를 저장소로 옮길 때만 쓰는 선택 절차다(멀티 서비스 플랫폼 스펙 10장 2단계). **클라우드에서 공통 플랫폼 작업을 시작하는 데 데스크톱·메모리 추출·요청 A 완료가 필요하지 않다.** 요청 B는 저장소만으로 시작한다.

**2026-10-30:** 공통 기능 현황 조사·현황표 작성 계획은 폐기했다. 요청 B에 있던 여섯 기능 전수 조사·표 작성·조사 결과 승인 대기는 제거했다. 공통 플랫폼 계획은 유지한다.

1단계(프롤로그 컴퓨터)는 2026-10-15 에 끝났다. 결과는 `docs/context/운영자-작업-방식.md`, `docs/context/개발-환경.md`, `docs/superpowers/plans/2026-10-11-갈피-AI-엔진-1단계-결정.md`.

- 구독 시작일 설정을 먼저 끝낸다(멀티 서비스 플랫폼 스펙 14장 "구독 시작일"). 지금 이 컴퓨터의 Claude 는 회사 계정이라, Claude Max 를 개인 계정으로 결제하고 로그인한 뒤에 붙여 넣는다
- 로컬 도구·플러그인은 이 기기에서 필요한 경우에만 준비한다. 클라우드 작업의 필수 조건으로 삼지 않는다
- 프롤로그 저장소를 별콩톡 저장소 옆 폴더에 받아 둔다. 요청 A 는 프롤로그의 운영자 작업 방식 문서를, 요청 B 는 플랫폼 스펙을 읽는다. 별콩톡을 받은 것과 같은 방식(HTTPS 또는 SSH)으로 받으면 된다. 계정이 하나뿐인 컴퓨터라 회사 노트북 같은 별칭은 필요 없다(`docs/context/개발-환경.md` 1장)

  ```bash

  ```

- 요청 A는 별콩톡 로컬 메모리를 옮길 때 사용한다. 요청 B는 A와 독립적으로 클라우드에서 실행할 수 있다

## 요청 A — 메모리를 저장소로 옮기기 (별콩톡 저장소에서)

````text
이 컴퓨터에 쌓인 Claude 메모리를 별콩톡 저장소 문서로 옮기려고 해. 앞으로 Claude Code 클라우드 세션과 Codex 도 같이 쓸 거라, 저장소에 없는 맥락은 없는 것으로 친다. 배경은 프롤로그 저장소의 docs/superpowers/specs/2026-10-15-멀티서비스-플랫폼-design.md 10장이고, 이번이 그 2단계야. 프롤로그 컴퓨터에서 한 1단계 결과는 프롤로그 저장소의 docs/context/ 에 있어. 프롤로그 저장소는 이 저장소 옆 폴더에 받아 뒀어(못 찾으면 물어봐).

1. 모으기
   - ~/.claude/projects/ 아래에서 이 저장소 경로에 해당하는 폴더(경로의 / 와 . 이 - 로 바뀐 이름)의 memory/ 를 전부 읽어. MEMORY.md 와 각 .md 파일 모두.
   - 이 저장소를 다른 경로에서도 연 적이 있으면 그 폴더의 memory/ 도 봐.
   - ~/.claude/CLAUDE.md(전역 지침)가 있으면 읽어.
   - 저장소 안의 CLAUDE.local.md, .claude/ 아래 설정, 커밋 안 한 파일 목록(git status)도 봐.
   - .env* 파일은 열지 마.

2. 나누기 — 메모리마다 아래 넷 중 하나로 분류해서 표로 먼저 보여 줘. 옮기기 전에 내 확인을 받아.
   (가) 이미 저장소 문서에 있음 → 어디에 있는지만 적는다
   (나) 오래 갈 프로젝트 지식·결정·운영자 취향 → 저장소로 옮긴다
   (다) 이 컴퓨터에만 해당하는 것(경로, 계정, 설치한 도구, 플러그인, MCP) → docs/context/개발-환경.md 로
   (라) 낡았거나 틀린 것 → 옮기지 않고 이유를 적는다

3. 옮기기
   - AGENTS.md 는 모든 세션에 자동으로 실리니 짧게 유지해(2026-07-27 에 30k 자에서 줄인 이유). 늘 지켜야 할 규칙만 AGENTS.md 에 넣고, 긴 내용은 docs/ 아래 문서로 두고 AGENTS.md 에는 한 줄 링크만 단다.
   - 지금 AGENTS.md 에는 "진행 중 작업·판정 스케줄은 메모리 w1-w7-work-queue 가 관리한다"고 적혀 있어. 그 큐를 저장소 문서(새로 만든다면 docs/BACKLOG.md)로 옮기고 AGENTS.md 의 그 줄을 새 위치로 고쳐. "진행 로그를 AGENTS.md 에 붙이지 않는다"는 규칙은 그대로 둔다.
   - 운영자 작업 방식(말투, 일하는 순서, 허락받을 것, 디자인 취향 등)은 docs/context/운영자-작업-방식.md 로. 프롤로그 저장소에 같은 이름의 문서가 있으니 먼저 읽고, 겹치는 것은 같은 표현으로 쓰고 별콩톡에만 해당하는 것은 따로 절을 둬. 나중에 platform 저장소에서 하나로 합친다.
   - 이 컴퓨터 설정은 docs/context/개발-환경.md 로. 설치된 Claude Code 플러그인과 MCP 서버는 이름만 적어.
   - 비밀값(키, 토큰, 비밀번호, .env 값)은 어디에도 옮기지 마. 메모리에 비밀값이 들어 있으면 그 사실만 알려 줘.
   - 메모리 파일은 지우지 마. 옮긴 뒤 정리는 내가 정한다.

4. 커밋
   - dev 브랜치에서 작업해. 문서만 바꾼다.
   - 커밋은 경로를 지정해서 해(git add -A 금지). 메모리에서 옮긴 문서와 AGENTS.md 수정은 커밋을 나눠.
   - 푸시는 내 확인을 받은 뒤.

5. 끝나면 알려 줄 것
   - 메모리마다 어디로 갔는지, 또는 왜 안 옮겼는지 표
   - 이 컴퓨터에만 남는 것(플러그인, MCP, .env, 커밋 안 한 파일)과 각각 어떻게 할지 제안
   - AGENTS.md 가 몇 글자에서 몇 글자가 됐는지
````

## 요청 B — 플랫폼 1단계 계획 (클라우드에서 독립 실행)

````text
멀티 서비스 플랫폼 작업을 클라우드에서 시작해. 저장소 문서를 기준으로 하고 데스크톱의 메모리·경로·키에 의존하지 마. 필요한 저장소는 현재 환경의 GitHub 연결로 접근해.

먼저 읽을 것
- 프롤로그 저장소: docs/superpowers/specs/2026-10-15-멀티서비스-플랫폼-design.md(v0.6), docs/context/운영자-작업-방식.md, docs/context/개발-환경.md
- 별콩톡 저장소: AGENTS.md, docs/context/

할 일 (스펙 14장 1-2, 선행 현황 조사 없음)
1. 스펙을 읽고 걸리는 점을 정리해 줘. 정할 게 있으면 한 번에 하나씩, 추천안을 먼저 붙여서 물어봐.
2. 공통 기능 현황 조사·현황표 작성과 그 결과 승인 대기는 폐기됐으니 실행하지 마. 공통 플랫폼 계획은 그대로야.
3. 스펙의 미결정 사항을 확인하고 1-2 구현 계획을 써. 범위는 platform 저장소(pnpm 모노레포) + ops(운영 요약 표준, 9장) + notify(Expo 푸시, 알림 규칙은 5장). 별콩톡 앱과 프롤로그가 둘 다 푸시를 쓴다는 걸 기준으로 잡아. 계획에는 스펙 9장 "역할 나누기"대로 작업마다 담당(Claude 또는 Codex)을 적어 줘. platform 은 Claude 가 주 담당, Codex 가 짝이야.
4. 계획 파일은 platform 저장소의 docs/superpowers/plans/ 에 둬. 스펙도 platform 저장소가 생기면 그쪽으로 옮기기로 했으니(스펙 머리말) 옮길 때 프롤로그에는 링크만 남겨.

지킬 것
- 별콩톡 보안 수정(스펙 12장 A)은 Codex 가 따로 맡는다. 이 세션에서는 하지 않는다.
- GitHub 조직 braveshine-labs 와 빈 platform 저장소는 내가 만든다. 아직 없으면 그 일만 남겨 두고 계획 초안은 먼저 써도 된다.
- 호스팅은 Vercel + Supabase, Railway 는 쓰지 않는다. 공통 패키지는 GitHub Packages 의 @braveshine-labs/* 로 낸다.
- 변경은 검토 가능한 PR로 남겨. 이 요청은 해당 브랜치 게시까지 포함해. 합치기는 내가 하고 자동 병합은 켜지 마. 운영 콘솔(Vercel·Supabase·토스) 작업과 비밀값 등록도 내가 한다.
- 비밀값은 저장소·문서에 넣지 않는다.
````
